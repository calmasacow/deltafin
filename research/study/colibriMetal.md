# colibri Metal/GPU deep-read (repo: research/colibri)

## 1. How the Metal backend works

### Architecture in one paragraph
Opt-in (`make colibri METAL=1` + env `COLI_METAL=1`), single-source Objective-C++ backend in `c/backend_metal.mm` (1039 lines) with API in `c/backend_metal.h`. The shader is a single MSL string compiled at runtime via `newLibraryWithSource:` (backend_metal.mm:426) — no Xcode/offline metalc needed. Everything exploits unified memory: there is no device list and no host<->device copy; resident weights are read zero-copy from the RAM they already occupy (backend_metal.h:11-16). Design driver stated in docs/metal.md:23-28: Metal's ~5 ms submit latency (backend_metal.h:127 says ~150 µs launch latency per command buffer) makes per-matmul dispatch a loss, so everything is batched into few command buffers per layer, and resident experts' GPU work is submitted *before* missed experts' disk reads so I/O and compute overlap.

### What runs on GPU vs CPU
GPU (all opt-in behind `g_metal_enabled`, every path falls back per-block to CPU on any fault):
- **Batched routed-expert SwiGLU** for one MoE block in ONE command buffer: `coli_metal_moe_block` / async two-phase `coli_metal_moe_block_begin`/`_end` (backend_metal.mm:904-1039). Per expert: gate GEMV → up GEMV → silu(gate)*up → down GEMV; scatter-add of `rw * hh` into the output is done **on CPU** in `moe_finish` (backend_metal.mm:979-982). The engine call site (colibri.c:3039-3158) submits the *resident* experts (pin∪LRU hits + shared expert on the first block) async BEFORE loading missed experts from disk, then a second sync submit for the just-loaded misses, then `_end` waits and scatters. A mandatory PIPE drain barrier sits before the miss-subset build (colibri.c:3135-3145) because the GPU would otherwise matmul half-loaded slabs. Blocks are processed 64 unique experts at a time (arrays `is_miss[64]`, `MG[65]` at colibri.c:3045-3048; slot 65 = shared expert).
- **Fused decode attention (S≤4)**: whole MLA attention layer in one command buffer, `coli_metal_attn_decode` (backend_metal.mm:687-716), gated at colibri.c:2344-2346 on: `!kvs` (no ragged batched-mux rows), `S<=4`, absorption mode, `kv_start==0` (full-range KV), and **hard-coded GLM-5.2 dims** `D==6144 && H==64 && q_lora==2048 && kv_lora==512 && qk_nope==192 && qk_rope==64 && vh==256 && kv_b.fmt==2 (int4)`. DSA sparse selection active (context > index_topk) also forces CPU (colibri.c:2347).
- **Full decode layer in ONE command buffer**: `coli_metal_layer_decode` (backend_metal.mm:724-824): in_ln rmsnorm → fused attention → residual add → post_ln → shared-expert gate/up/silu/down → router matvec+sigmoid → exact top-K select. Engine gate additionally requires `n_experts==256 && topk==8 && n_shared==1 && moe_inter==2048` (colibri.c:4068-4072). CPU keeps only expert resolve/disk loads + expert CBs + scatter. Outputs routing (idx/w/keff) back to CPU which then calls `moe()` with the pre-computed routing (colibri.c:4112-4115).
- **Prefill large GEMMs**: `coli_metal_gemm` dispatched from `matmul_qt` when `S >= COLI_METAL_GEMM_MIN` (default 16), fmt int8/int4 only, not under `omp_in_parallel()` and not while speculation-pinned (colibri.c:530-533).

CPU keeps: everything else — tokenization/sampling/MTP, expert disk I/O, scatter-add, DSA indexer key projection (still CPU even when layer CB succeeds, colibri.c:4099-4106), S>4 attention, ragged mux decode, partial-KV windows, non-GLM dims, int2 experts, and any faulted GPU block.

### Buffer management / unified memory
- **Everything is `MTLResourceStorageModeShared`** — there are zero private-storage buffers in the file (g_res_opts at mm:304). `COLI_METAL_UNTRACKED=1` adds `MTLResourceHazardTrackingModeUntracked` (mm:417-418).
- **Zero-copy slab registry**: `coli_metal_register(base,len)` wraps page-aligned (16384-byte Apple page) host allocations once via `newBufferWithBytesNoCopy` and stores them in `g_slabs` (mm:479-498); `resolve(ptr)` maps any host pointer inside a registered range to `(MTLBuffer, gpuAddress+offset)` (mm:509-515). Registered by the engine: expert weight/scale slabs on every (re)alloc (colibri.c:1528-1563, 1743-1763), the aligned-alloc path for resident weights (colibri.c:745-748), mmap'd regions (colibri.c:1318-1319), and the KV Lc/Rc caches (colibri.c:4237-4246). Non-aligned pointers fall back to a copying `newBufferWithBytes` (mm:408-413).
- **Bindless dispatch**: for a MoE block, per-expert raw `gpuAddress` values are collected into small shared buffers (`bag/bau/bad/bsg/bsu/bsd`, mm:914-929); residency is declared with a per-CB `useResource:` loop over the deduped buffer list (mm:943-945) — **whose cost scales with LRU cache size**, which motivated:
- **E5 residency-set experiment** (`COLI_METAL_RESSET=1`, macOS 15+): one persistent `MTLResidencySet` attached to the queue replaces the per-CB `useResource:` loop; adds are deferred/batched and flushed at the next `moe_submit`, removes commit immediately before host free (mm:327-391, 456-474; SUMMARY.md). Prior E4 (MTLHeap) data: batching residency declaration cut the GPU stall **25.9 s → 3.9 s (−85%) at cap16** but heap-backed allocation cost **+12–13 s expert-disk-load tax** (SUMMARY.md "The hypothesis"); E5 keeps malloc slabs and moves only the bookkeeping. A key concurrency rule: no live Metal call under `g_slab_mtx` (the OMP loader threads contend on it).
- **Activations**: memcpy into grow-only shared scratch (`ensure()`, mm:395-398), results memcpy'd back after `waitUntilCompleted` — all synchronous per CB except the two-phase MoE begin/end.
- **Keep-alive spinner** `COLI_METAL_SPIN=1` (mm:517-542): trivial GPU work on its own queue so the GPU doesn't ramp clocks down between short per-layer bursts (explicitly an experiment to quantify clock-ramp share of submit latency).
- Diagnostics: `coli_metal_moe_counts/times/kernel_time`, `attn_counts/lat` split wall vs kernel vs schedule latency; printed in the profile footer (colibri.c:4744-4752).

From docs/metal.md, docs/benchmarks.md:87-90, and docs/METAL-M5MAX-PERF-REPORT.md. Model in ALL cases: GLM-5.2 int4 (744B MoE, ~370 GB container on disk), experts streamed from SSD. ### METAL-M5MAX-PERF-REPORT.md in full
Setup held fixed: M5 Max (12P+6E, 40-core GPU, 128 GB), GLM-5.2 int4, 1024 tokens, `COLI_METAL=1 DIRECT=1 MTP=0 --ram 110`; every run ~607 experts/token, 74–75% hit, RSS ~97.9 GB, `fallback CPU 0` (all eligible blocks on GPU).

| config | tok/s | wall s | expert-disk | expert-matmul | attention | attn GPU kernel | expert GPU overhead |
|---|---|---|---|---|---|---|---|
| A old base | 2.06 | 496 | 266 | 109 | 100 | 76 | 51 |
| B rebased defaults | 1.25 | 819 | 285 | 215 | 290 | 223 | 106 |
| C B+`PIPE=1` | 1.30 | 788 | 297 | 190 | 272 | 212 | 89 |
| D B+`COLI_NO_OMP_TUNE=1` | 1.90 | 539 | 266 | 143 | 109 | 85 | 84 |
| **E D+`PIPE=1 PIPE_WORKERS=8`** | **2.24** | **457** | **241** | **97** | **99** | **79** | **44** |

Expert *kernel* time was constant ~34–35 s in every un-throttled run; "expert GPU overhead" = GPU idle waiting to be fed. Mechanism of the B regression: the OMP hot-team **active spin** keeps the CPU ~97% busy-waiting on the GPU; on M-series the CPU and GPU share one power/thermal envelope, so the spin robs the GPU of clock headroom — attention kernel time **tripled 76→223 s for identical work** (same ≈140k blocks, 79,794 attention launches, 618k experts-on-GPU). `COLI_NO_OMP_TUNE=1` restores GPU clocks (223→85 s) but passive waits slow CPU→GPU handoff (+33 s expert overhead); `PIPE=1 PIPE_WORKERS=8` hides that (84→44 s) and trims disk 266→241 s. **The two levers are complementary: NO_OMP restores GPU clocks; PIPE hides the dispatch latency NO_OMP introduces.** Report recommends Metal builds default to passive OMP wait.
Other findings: `DIRECT=1` is required, not optional — `DIRECT=0` was **~2× slower (2.16→1.15 tok/s)** because reads fall back to page cache which breaks zero-copy GPU slab registration (adds a copy to feed the GPU). Memory ceiling on 128 GB: `--ram 110` safe (RSS ~97 GB); `--ram 120` crosses into memory compression (double penalty: compressor CPU cost + SoC power stolen from GPU). MTP=0 throughout; the rebase made MTP verify (S≤4) GPU-accelerated, so MTP-on is a live untested lever. Run-to-run non-deterministic under PIPE/threads (fp non-associativity in parallel expert-sum reductions) but throughput identical; "token-exact" holds only under a serial/deterministic validation config.

## 3. Tuning knobs that matter (docs/ENVIRONMENT.md, docs/tuning.md, docs/SETTINGS.md)

**Metal-specific:** `COLI_METAL=1` (needs METAL=1 build; requested-but-unavailable exits with code 2, colibri.c:6521-6523); `COLI_METAL_GEMM_MIN` (default 16, min matmul rows to GPU); `COLI_METAL_SPIN=1` (keep-alive spinner, less dispatch latency / more power); `COLI_METAL_UNTRACKED=1` (untracked hazard mode); `COLI_METAL_RESSET=1` (macOS 15+ residency set, experimental); `COLI_RTOP8` (default ON parallel top-8; `=0` serial).

**Critical companions on Apple Silicon:** `COLI_NO_OMP_TUNE=1` (kill-switch for OMP active-spin+proc-bind; **the single highest-impact setting with Metal**); `PIPE=1` + `PIPE_WORKERS` (default 8; ENVIRONMENT.md's worked Apple config uses 6; M5 report used 8) — async expert-load pool, −18% disk service; `DIRECT=1` (macOS: F_NOCACHE; preserves zero-copy GPU path; +65% alone measured on Strix Halo); `MTP=0` (net loss on measured Metal configs so far); `MLOCK` default **auto-ON on macOS** (wires expert cache to dodge the memory compressor); `--ram/RAM_GB` (default auto ≈88% of free; on 128 GB the knee is 110 — Metal registered buffers share unified memory so the knee is lower than a CPU-only build suggests).

**Cache/residency policy:** `PIN=auto`/`PIN=stats.txt` + `PIN_GB` (default 10 GB) pins hottest experts from `.coli_usage` history; `AUTOPIN=1` (auto after ≥5000 selections — "gets faster the more you use it": M5 Max warmed 1.11→1.83, Framework 0.16→0.40 over five runs); `CAP_RAISE=1` (auto-grow LRU cap to fill `--ram`); `--cap` (start 8/layer); `REPIN=N` live re-pin; `--repin`; `PREFETCH` depth; `PILOT=1`/`PILOT_REAL=1`/`PILOT_TWO=1` router-lookahead prefetch (L+1 router on layer-L state recalls 71.6% of true top-8 vs 41.3% for last-token identity; PILOT_REAL +11pp hit; Strix Halo hit 1.83 tok/s with `DIRECT=1 PIPE=1 PILOT_REAL=1 PILOT_TWO=1`); `--topp 0.7` adaptive expert top-p (30–40% less disk, lossy, 1.6× on a small-RAM box); `KVSAVE=1` KV persistence (~182 KB/token) → zero re-prefill on reopen; `COLI_MODEL_DIRS`/`COLI_MODEL_MIRROR`/`COLI_DISK_WEIGHTS` multi-drive expert striping.

**Doc'd Apple-Silicon reference command** (ENVIRONMENT.md:196-206): `COLI_METAL=1 DIRECT=1 COLI_NO_OMP_TUNE=1 PIPE=1 PIPE_WORKERS=6 MTP=0 ./coli run --ram 113` (add `COLI_TEMP=0` for reproducible greedy). Note a doc discrepancy: tuning.md:22 calls PIPE "default ON", ENVIRONMENT.md:41 says default 0/off — set it explicitly.

## 4. CACHE_ROUTE (docs/CACHE_ROUTE.md)
Opt-in **cache-aware MoE routing** (default OFF), paper-style max-rank selection (arXiv:2412.00099): always keep the true top-`ROUTE_J` (default 2) experts; fill the remaining K slots preferring experts already **resident** (pin∪LRU) that still rank inside the top-`ROUTE_M` (default 12) window. It is routing-side — it can *change which experts run* (unlike PILOT, which prefetches without changing IDs). Knobs: `CACHE_ROUTE`, `ROUTE_J`, `ROUTE_M`, `ROUTE_P` (cumulative-mass window alternative), `ROUTE_ALPHA` (down-weight substituted experts), `ROUTE_AGREE` telemetry (overlap% + KL vs true top-K; also `swap%`, `route_swaps/slots`, `route_kl`). Works on plain CPU streaming (no GPU patches needed). Measured payoff: DGX Spark GB10 went **2.4 → 3.33 tok/s** with CACHE_ROUTE (#199, benchmarks.md:103). Explicitly experimental until `./coli bench` quality gates pass; do not default on.

## 5. Build system (c/Makefile)
- `make colibri METAL=1` — macOS only (`$(error METAL=1 is supported only on macOS)` otherwise, Makefile:250-252). Adds `-DCOLI_METAL` to CFLAGS and `-framework Metal -framework Foundation -lc++` to LDFLAGS (Makefile:253-254). `backend_metal.mm` is compiled with `clang++ -x objective-c++ -std=gnu++17 -fobjc-arc -O3` (Makefile:248, 307-308). Shader compiles at runtime → no Xcode.
- `make metal-test` builds+runs `tests/test_backend_metal.mm` standalone kernel/attention correctness vs CPU reference (Makefile:310-312), including r_top8 serial/parallel memcmp equivalence for E=24/168/256.
- macOS base: `CC=clang`, OpenMP only via Homebrew `libomp` (`-Xclang -fopenmp`); if absent it **builds single-threaded with a warning** (Makefile:40-56). No `-march` (NEON is arm64 baseline); optional `ARCH=native` appends `-mcpu=native` which unlocks the i8mm SMMLA int8/int4 CPU dot kernels — note **M1 lacks i8mm** (ARMv8.6 feature), so those CPU kernels won't engage on M1 Max; M4/M5 have them (relevant to why the GPU path matters more on M1).
- `CUDA=1`/`HIP=1` are refused on macOS. `.build-config` stamp forces relink when flags change (Makefile:271-284). `COLI_CUDA` and `COLI_METAL` can't co-exist on a Mac build; contrast: the CUDA tier deliberately keeps streaming experts on CPU (PCIe copy tax, docs/cuda.md:3-6) whereas Metal streams them to GPU zero-copy — unified memory is exactly what removes CUDA's structural excuse.

## 6. Known bottlenecks / limitations (admitted in docs or code)
1. **Shared SoC power envelope**: CPU spin-waiting throttles GPU clocks (−39% trap; M5MAX report). Needs `COLI_NO_OMP_TUNE=1`, which in turn needs `PIPE=1` to hide the slower CPU→GPU handoff.
2. **Command-buffer submit latency** (~5 ms submit / ~150 µs launch) forces coarse batching; GPU clock ramp-down between short per-layer bursts is real enough that a keep-alive spinner exists (`COLI_METAL_SPIN`).
3. **Hard-coded GLM-5.2 shapes** in the fused attention/full-layer kernels (D=6144, H=64, q_lora=2048, kv_lora=512, nope=192, rope=64, vh=256, kv_b must be int4; layer CB additionally E=256, K=8, 1 shared expert, moe_inter=2048). Any other model (i.e., Kimi K3) silently falls back to CPU for attention/layer; only the **MoE block path is shape-generic** (D/Iinter parameters) and only for int8/int4 (`fmt!=1 && fmt!=2 → nil`, mm:909). **int2 experts are unsupported on the GPU MoE path** (only `mm_gemv` handles fmt 3).
4. Fused attention limited to **S≤4** (AMAXS=4), `st0==0` full-range KV, no ragged per-row KV (batched mux decode → CPU, colibri.c:2338-2343), and disabled once **DSA sparse selection activates** (context length > index_topk) — long-context decode drops back to CPU attention.
5. **CPU scatter-add** after every MoE block (moe_finish) and memcpy of activations in/out of shared scratch per CB — per-token CPU work on the critical path.
6. **Residency declaration cost scales with LRU cache size** (per-CB `useResource:` loop) — E4 measured a 25.9 s GPU stall at cap16 from it; E5 residency set (macOS 15+, experimental) is the fix in flight; E4's heap variant added +12–13 s disk-load tax (SUMMARY.md).
7. **Memory compressor cliff**: over-budget `--ram` triggers macOS compression — double penalty (CPU cost + shared power). MLOCK auto-on mitigates; knee is lower than CPU-only because GPU-registered buffers share unified memory.
8. **No true O_DIRECT on macOS**: `DIRECT=1` uses F_NOCACHE, which can't evict already-cached pages (benchmarks.md:48-50) — benchmark reads are easily contaminated; but DIRECT=1 is still ~2× faster end-to-end because it preserves zero-copy slab registration.
9. **Non-determinism** run-to-run under PIPE/parallel reductions (argmax flips at token boundaries); "token-exact vs CPU" holds only in serial validation configs. (Contrast CUDA/HIP: float GPU matmuls are *not* token-identical to CPU IDOT at all, and MTP acceptance drops ~40%→31% on GPU-heavy configs, GPU_BACKENDS.md:76-80.)
10. `coli_metal_matmul` (tensor-wrapping path) allocates fresh x/y buffers per call; prefill GEMM/gemm path uses grow-only scratch instead. Attention inner loops (a_qabs/a_score/a_clat/a_ctx) are naive serial-per-thread loops, adequate for S≤4 decode, not a prefill engine — prefill relies on `mm_gemv` GEMV-style kernels, no simdgroup_matrix/MMA anywhere.
11. GEMV kernels assume SIMD width 32; `r_top8_par` hard-disabled if `threadExecutionWidth != 32` (mm:445-452). E>256 routing falls back to serial kernel (Kimi K3 has 384+ experts per common reports — would hit this).

## KEY FACTS
- colibri Metal backend is one Objective-C++ file c/backend_metal.mm (1039 lines) + backend_metal.h; shader is runtime-compiled MSL (newLibraryWithSource), no Xcode required; build: make colibri METAL=1 -> -DCOLI_METAL, -framework Metal -framework Foundation, clang++ -x objective-c++ -std=gnu++17 -fobjc-arc -O3 (c/Makefile:244-255,307-308)
- All Metal buffers are MTLResourceStorageModeShared (unified memory, zero private storage); expert/KV slabs are wrapped zero-copy with newBufferWithBytesNoCopy when 16384-byte page aligned, and resolve() maps host pointers to gpuAddress offsets (backend_metal.mm:304,408-413,479-515)
- GPU ops: batched routed-expert SwiGLU per MoE block in one command buffer (bindless moe_gemv over gpuAddress arrays), fused S<=4 decode attention in one CB, full decode layer (norms+attention+residual+shared expert+router+top-K) in one CB, and prefill GEMMs when S>=COLI_METAL_GEMM_MIN (default 16); CPU keeps disk I/O, scatter-add, sampling, MTP, S>4, ragged/mux rows, DSA-active layers
- Fused attention/layer kernels hard-code GLM-5.2 dims: D=6144, H=64, q_lora=2048, kv_lora=512, nope=192, rope=64, v_head=256, kv_b int4; layer CB also requires E=256, K=8, 1 shared expert, moe_inter=2048 (colibri.c:2344-2346,4068-4072) — Kimi K3 would fall back to CPU on these paths; only the MoE-block path is shape-generic (int8/int4 only, no int2)
- moe_gemv kernel measured 358-389 GB/s on engine-like block shapes (backend_metal.mm:68-69 comment); parallel top-8 select r_top8_par is ~93x faster than the serial kernel which cost 0.465 ms/layer = ~55% of the layer command buffer (mm:222-241); r_top8_par contract E<=256, falls back to serial beyond
- M5 Max (12P+6E, 40-core GPU, 128GB) best published number: 2.24 tok/s decode on GLM-5.2 744B int4 with COLI_METAL=1 DIRECT=1 MTP=0 COLI_NO_OMP_TUNE=1 PIPE=1 PIPE_WORKERS=8 --ram 110 (1024 tokens, 74-75% expert hit, RSS ~97.9GB) — docs/METAL-M5MAX-PERF-REPORT.md
- OMP active-spin trap: default hot-team spin steals the shared M-series SoC power budget from the GPU — attention GPU kernel time tripled 76s->223s for identical work, throughput 2.06->1.25 tok/s (-39%); COLI_NO_OMP_TUNE=1 restores GPU clocks and PIPE=1 hides the resulting CPU->GPU dispatch latency; the two levers are complementary and both required
- DIRECT=1 (F_NOCACHE on macOS) is required with Metal, not optional: DIRECT=0 measured ~2x slower (2.16->1.15 tok/s) because page-cache reads break the zero-copy GPU slab registration; macOS has no true O_DIRECT so cold-read benchmarks need a fresh shard or reboot
- Other Apple datapoints: M4 Max 128GB CPU 0.30 -> Metal 0.42 tok/s (~1.4x, MTP on); M5 Max CPU-only 1.06 tok/s; M5 Max Metal --ram 96 with 39.7GB pin 1.83 tok/s (warmed 1.11->1.83); 46.9GB learned pin --ram 110 2.06 tok/s at 72.5% hit; Mac Mini M4 Pro 48GB Metal --ram 38: 0.30 tok/s vs 0.18 CPU (closest analog to 64GB M1 Max)
- Memory ceiling on 128GB M5 Max: --ram 110 safe (RSS ~97GB), --ram 120 crosses into macOS memory compression (double penalty: compressor CPU + SoC power stolen from GPU); MLOCK defaults auto-ON on macOS to wire the expert cache; RAM_GB default auto ~= 88% of free RAM
- Metal launch latency ~150us per command buffer (~5ms submit per docs/metal.md), motivating one-CB-per-layer batching and the resident-experts-submitted-before-disk-reads overlap; a COLI_METAL_SPIN=1 keep-alive spinner exists because GPU clocks ramp down between short per-layer bursts
- Residency declaration (per-CB useResource: loop) scales with LRU cache size; E4 MTLHeap experiment cut GPU stall 25.9s->3.9s (-85%) but added +12-13s disk-load tax; E5 (COLI_METAL_RESSET=1, macOS 15+, MTLResidencySet attached to queue) keeps malloc slabs and moves only residency bookkeeping (SUMMARY.md)
- CACHE_ROUTE=1 (default OFF, experimental): max-rank cache-aware routing per arXiv:2412.00099 — always take true top-ROUTE_J (2), fill remaining slots with resident (pin∪LRU) experts inside top-ROUTE_M (12); changes expert IDs; measured 2.4 -> 3.33 tok/s on DGX Spark GB10 (#199)
- PILOT router-lookahead prefetch: applying layer L+1's router to layer L's state recalls 71.6% of true top-8 (vs 41.3% last-token identity); PILOT_REAL=1 +11pp hit; Strix Halo reached 1.83 tok/s with DIRECT=1 PIPE=1 PILOT_REAL=1 PILOT_TWO=1
- Learning cache: .coli_usage appended every turn, AUTOPIN after >=5000 selections, PIN=auto + PIN_GB; engine auto-raises LRU cap to fill --ram (CAP_RAISE=1); --topp 0.7 adaptive expert top-p cuts disk 30-40% (lossy) and bought 1.6x on a small-RAM box; KV cache persists at ~182 KB/token for zero re-prefill
- GLM-5.2 744B int4 container is ~370GB on disk; cold decode costs ~11GB expert reads/token; macOS OpenMP needs Homebrew libomp or the build is single-threaded; M1 lacks i8mm so ARCH=native SMMLA int8/int4 CPU kernels do not apply on M1 Max (they do on M4/M5)
- Non-determinism: with PIPE/parallel reductions two identical greedy runs diverge within ~7 tokens (fp non-associativity flips argmax); throughput is stable; 'token-exact vs CPU' holds only under serial validation configs
- Documented Apple-Silicon reference command (docs/ENVIRONMENT.md:196-206): COLI_METAL=1 DIRECT=1 COLI_NO_OMP_TUNE=1 PIPE=1 PIPE_WORKERS=6 MTP=0 ./coli run --ram 113 (COLI_TEMP=0 for reproducible greedy); doc discrepancy: tuning.md calls PIPE default ON, ENVIRONMENT.md says default 0 — set explicitly

## IMPROVEMENT IDEAS
- Port the fused attention/layer kernels' compiled-in dims to Kimi K3's architecture (or parameterize via Metal function constants): as shipped, any non-GLM shape (D!=6144, kv_lora!=512, E!=256, K!=8) silently falls back to CPU attention/routing — on M1 Max only the shape-generic MoE-block path would run on GPU day one
- Kimi K3 at 2.8T params likely exceeds 1.2TB free NVMe at int4 (GLM 744B int4 = ~370GB, so 2.8T ~ 1.4TB); plan for int2/int3 expert quantization or REAP expert pruning (repo already handles E=168 REAP packages) — and note colibri's GPU MoE path (moe_gemv) supports only int8/int4, so an int2 lane must be added to moe_gemv (mm_gemv already has fmt=3 int2 dequant code to copy from)
- Bake in the two proven Apple-Silicon levers from day one: passive OMP wait (COLI_NO_OMP_TUNE=1 semantics — active spin costs -39% by throttling GPU clocks in the shared power envelope) plus an async expert-load pool (PIPE=1, 6-8 workers) to hide the passive-wait dispatch latency; on a 10-core M1 Max the spin penalty is proportionally worse than on 18-core M5 Max
- Use F_NOCACHE (DIRECT=1) reads into page-aligned slabs registered zero-copy with newBufferWithBytesNoCopy — the M5 report showed buffered reads are ~2x slower end-to-end because they break zero-copy GPU feeding; on 64GB the --ram knee will be roughly 50-54GB (M4 Pro 48GB used --ram 38; scale ~0.8x of RAM), with mlock to dodge the macOS compressor
- Adopt queue-attached MTLResidencySet (macOS 15+) from the start instead of per-CB useResource: loops — colibri's E4 data shows batched residency declaration cuts GPU stall by 85%, and their E5 shows how to do it without the heap-allocation disk-load tax (malloc slabs + deferred batched addAllocation commits, removes committed before free)
- Beat colibri's GEMV-only prefill: add simdgroup_matrix (8x8 MMA) tiled GEMM kernels for prefill and MTP-verify batches — colibri has no MMA anywhere and its a_qabs/a_score attention loops are naive serial-per-thread; M1 Max (Apple7 family) supports simdgroup_float8x8, and prefill is where the 400GB/s M1 Max GPU can actually be compute-fed
- Exploit cache-aware routing aggressively on the RAM-starved 64GB target: CACHE_ROUTE-style max-rank substitution bought +39% on a 121GB host (2.4->3.33 tok/s); at ~50GB pin for a 2.8T model the hit rate will be low, so routing-side residency preference plus router-lookahead prefetch (PILOT: 71.6% next-layer recall) matter more than on the 128GB machines colibri was tuned on
- Copy the one-command-buffer-per-layer + resident-experts-submitted-before-disk-reads overlap pattern exactly (coli_metal_moe_block_begin before misses' preads, second CB for loaded misses): it took M5 Max expert-GPU-idle from 84s to 44s; also keep a keep-alive spinner option since Apple GPUs down-clock between short per-layer bursts
- Move the scatter-add and activation staging off the CPU: colibri memcpys activations into shared scratch and scatter-adds expert outputs on CPU after waitUntilCompleted — writing results directly into a shared out-buffer with a GPU scatter kernel and using untracked hazard mode would remove per-token CPU work that competes with I/O threads on the 10-core M1 Max
- Extend the parallel top-K select beyond E<=256: colibri's r_top8_par (93x faster than serial, which was 55% of the layer CB) falls back to the slow serial kernel for E>256 — Kimi K3's expert count (if >256) needs a two-level or multi-simdgroup reduction variant
- Consider multi-drive expert striping (COLI_MODEL_DIRS) with an external TB4/USB4 NVMe: on M1 Max internal SSD (~5-6GB/s) decode is disk-bound at low hit rates and colibri's per-shard search-path striping parallelizes cold expert reads across drives — likely necessary given the model may not even fit on the internal 1.2TB free
- Test MTP speculation on-GPU: colibri measured MTP as a net loss pre-rebase and never re-tested after fused attention covered S<=4 verify forwards ('a live, unexplored lever' per the M5 report) — Kimi K3 ships an MTP head and on a slow-decode machine 2.2-2.8 tok/forward acceptance could be the single biggest multiplier if the S=4 verify runs in the fused GPU path
