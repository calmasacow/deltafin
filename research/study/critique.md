# Completeness critique: Kimi-K3-on-M1-Max plan

Verification performed during this review: HF `moonshotai/Kimi-K3` (config.json, resolve URL, and `/api/models`) all returned **HTTP 401 at 14:59–15:01 UTC on 2026-07-27**, i.e. at and past the scheduled drop time — everything architectural in the six reports is still unconfirmed preview material. I also read code the agents did not report on: colibri ships a **disk-safe shard-by-shard download→convert→delete pipeline** (`research/colibri/c/tools/convert_fp8_to_int4.py`, header lines 1–30: "scarica UNO shard (~5GB), lo converte, lo CANCELLA"; `--min-free-gb` guard line 366; resume manifests lines 542–582; multi-stream Range downloader lines 652–738; **NVFP4 e2m1 LUT already present** lines 138–144, verified 1:1 vs `ml_dtypes.float4_e2m1fn`), a from-HF downloader (`c/download_fp8.py`, note `DEST = r"I:\glm52_fp8"` — a hardcoded Windows path), a `tokenizer.json` BPE loader (`c/tok.h:1-11`, cl100k/o200k regex families only), and a hand-ported GLM chat template in C (`c/colibri.c:5615`). Licenses verified: colibri = Apache-2.0, ds4 = MIT (`LICENSE` in each repo root). ds4 has zero jinja/chat-template code (grep confirmed).

## Top 10 gaps, ranked by expected damage

### 1. Every K3 architecture number is unverified — and the repo was still 401 at drop time
The plan's load-bearing constants (93 layers, 896 experts, 16 active, MLA-every-4, hidden size, moe_intermediate, shared-expert count, KDA head dims, MTP presence, vision tower size) come from a vLLM preview blog, not a config. Expert byte-size (18MB vs 23MB if K2's moe_inter=2048/hidden=7168 carry over: 3×2048×7168×4.25/8 ≈ 23.4MB) swings disk fit, cache-entry count, and the 0.2 tok/s cold ceiling by ±30%. The persistent 401 also signals the repo may be **license-gated** (click-through + HF token), which breaks every scripted download path until a human accepts.
**Close it:** poll `https://huggingface.co/api/models/moonshotai/Kimi-K3` (and `-Instruct`/`-Thinking`/`-Base` name variants, plus ModelScope mirror) with an authenticated token; the moment it clears, pull `config.json` + `modeling_*.py` + `tokenizer_config.json` + `chat_template.jinja` (a few MB total) and re-derive ALL sizing before any kernel or conversion work. Diff against the vLLM K3 tree, which Moonshot contributed to directly.

### 2. Conversion pipeline: right skeleton exists, wrong format, and total wall-clock never estimated
The prompt's premise ("block-fp8 safetensors, ~2.8TB") conflicts with kimiArch's finding (MXFP4 release, ~1.5TB) — a 2x difference in download volume and completely different dequant math; **nobody flagged or resolved this**. colibri's converter is the correct disk-staging pattern (peak disk = 1 shard + growing output; output at E8/IQ3 ≈ 1.07TB leaves <100GB margin on 1.2TB free — the default `--min-free-gb 20` needs raising), but it is GLM-specific: e4m3 + 128×128 `weight_scale_inv` dequant, GLM tensor names, GLM skip-list. For K3 it needs: MXFP4 e8m0-per-32 scale handling (the e2m1 LUT exists; the scale layout differs from the NVFP4 path already coded), K3 tensor-name classification (KDA/conv/AttnRes/vision/router), un-stacking fused `[E,…]` expert tensors into file-adjacent 4KiB-aligned per-expert gate/up/down triplets (16KiB-aligned slab boundaries for Metal no-copy), and fp8-vs-MXFP4 source branching. **Unmeasured:** the user's actual download bandwidth (1.5–2.8TB at 40MB/s = 10–19 days; at 1GB/s = 4–8h — this single number may dominate week one) and numpy convert throughput per shard (is convert or download the bottleneck? determines pipeline parallelism). Nothing about `caffeinate`/sleep-prevention for a multi-day run.
**Close it:** today, before the drop clears — download one K2.5 shard and measure real HF/ModelScope bandwidth; benchmark the converter's MB/s on that shard; write the MXFP4 dequant branch against `ml_dtypes`/K2.5-int4 fixtures; compute and publish the end-to-end hours-to-first-token estimate.

### 3. No numerical-correctness harness for three brand-new ops (KDA-variant, AttnRes, SiTU)
No engine anywhere has KDA-for-K3 (only Triton/CUDA for the Kimi-Linear variant; K3's KDA adds channel-wise gating + DPLR transition), AttnRes, or SiTU — and **nobody defined what SiTU actually is** (if it replaces SwiGLU inside experts, both engines' fused gate/up/act kernels are wrong as designed). A 2.8T model cannot be run at reference precision on this box, so bugs will present as subtly degraded text, not crashes. Both donor engines are built around oracles (colibri: `tools/make_glm_oracle.py` tiny-model token-identical oracles; ds4: avg_nll vs official API continuations) — the plan inherits neither.
**Close it:** (a) build a per-layer PyTorch oracle from `modeling_kimi.py` that streams one layer's weights at a time (≈18–23GB/layer of experts fits in 64GB transiently) and dumps activation fixtures for KDA/AttnRes/SiTU/MLA/router; (b) use llama.cpp PR #18755 as a C reference for the Kimi-Linear KDA baseline; (c) budget ~$10–50 of K3 API ($3/M in) for ds4-style avg_nll end-to-end gating of every quant tier.

### 4. Tokenizer and chat template: colibri's loader cannot read what Moonshot ships
K-family repos ship `tiktoken.model` + `tokenization_kimi.py` (trust_remote_code), not necessarily a `tokenizer.json`; colibri's `tok.h` parses only `tokenizer.json` with cl100k/o200k pre-tokenizer regexes (tok.h:1-24), and Kimi's regex must be verified against `tokenization_kimi.py` — a wrong split regex silently changes tokenization on edge cases. The chat template (incl. tool-calling via `tool_declaration_ts.py`, thinking sections, K3's "max thinking effort" control) must be hand-ported to C — colibri did this for GLM (colibri.c:5615), ds4 hardcodes DSML with byte-exact replay (its KV-cache keying depends on byte-identical re-rendering; K3 needs the same discipline).
**Close it:** today, using public K2.5: write tiktoken.model→tokenizer.json conversion (or a tiktoken loader), round-trip-test 10k samples vs `transformers` `apply_chat_template`/encode as oracle; port the K3 jinja when it lands and add byte-exact template tests.

### 5. No hit-rate/throughput model for 896-experts×16-active against a ~30–40GB cache
All speed expectations extrapolate GLM-5.2 (256 experts/8 active, 74–75% hit with a 46.9GB pin on a **128GB** machine). K3 has ~82k routed experts (896×~92); 40GB/20MB ≈ 2000 cached = **2.4% coverage**. Under near-uniform routing, decode ≈ 16×92×20MB×0.97 ≈ 28GB/token → 0.23 tok/s — i.e., the entire plan's viability rests on routing skew that nobody has measured for any K-family model. PILOT's 71.6% next-layer recall is GLM-measured; KDA-hybrid routing predictability is unknown. CACHE_ROUTE's quality cost at rank-12 substitution on K3 is unknown.
**Close it:** first weights-day deliverable = router trace study: run the per-layer oracle (gap 3) over ~1M calibration tokens, dump per-layer expert selection frequencies + cross-layer co-activation (extend colibri's `expert_atlas`/`route_pairs.py` and ds4's hotlist profiler), and produce the hit-rate-vs-pin-GB curve. This number decides whether the target is 0.3 or 2 tok/s and whether expert pruning is mandatory rather than optional.

### 6. Prefill is undesigned and may dominate real usage
ds4's prefill strategy pages in the **full expert set per layer**; for K3 that is 896×~20MB ≈ 18GB/layer — at 6.6GB/s that's ~2.7s/layer × ~92 layers ≈ 250s per prefill pass regardless of chunk size (amortized ≈ 16 tok/s ceiling at 4096-chunk, but a 30-second first-token stall per cold agentic prompt). Also 18GB/layer barely fits the RAM budget transiently, making ds4's 2-layer double-buffer reserve infeasible. Nobody sized KDA chunkwise prefill throughput on CPU/Metal (no kernel exists), and nobody carried over the session-persistence mitigations (ds4 KVC files, colibri `.coli_kv`, KDA state is only ~150MB so K3 session files would be tiny and instant).
**Close it:** design prefill explicitly: layer-major expert streaming with capped in-flight bytes, persistent KV+KDA-state session files keyed by rendered-byte SHA1 (port ds4's KVC discipline verbatim), and measure whether CPU NEON can even feed KDA chunkwise scan at >100 tok/s prefill.

### 7. Sub-4-bit requant of a QAT'd-MXFP4 model is quality-unvalidated, and imatrix calibration is chicken-and-egg
Disk forces ≤3.2bpw average (E8/IQ3 3.0625 → ~1.07TB), but K3 was QAT'd at exactly MXFP4 — requantizing below the QAT format may degrade disproportionately, E8/IQ3 needs activation-rotation statistics, and imatrix needs to *run the model you can't yet fit*. The cfse/rANS lossless layer (1.37x on int4) was never benchmarked for decode MB/s/core, and its ratio on MXFP4/IQ3 payloads (different statistics than white int4 nibbles) is unknown.
**Close it:** rehearse on K2.5 (public, 595GB, same QAT-int4 lineage): requant its routed experts to 3.0625/2.5bpw tiers, measure avg_nll delta vs Moonshot API; benchmark nibble-rANS decode throughput per E-core; evaluate the alternative fit levers — usage-ranked expert pruning, MXFP4-hot/2bit-cold tiering, vision-tower omission — with actual numbers instead of assertions.

### 8. Day-one GPU coverage for K3 is ~zero; the port sequence is unplanned
Everything fast in both engines is shape-hardcoded and violated by K3: colibri fused attention/layer CBs require GLM dims (colibri.c:2344-2366) and its GPU MoE path is int8/int4-only (no IQ3/IQ2/MXFP4 dequant in `moe_gemv`); `r_top8_par` caps at E≤256 (K3 needs top-16-of-896, a new two-level reduction); ds4 hard caps at 80 layers/384 experts/8 active with sum6/sum8 kernels. No Metal or NEON KDA kernel exists anywhere. Unless the port is sequenced, week one ends with CPU-only decode of the streamed experts and none of the measured Metal wins.
**Close it:** explicit kernel roadmap in dependency order: (1) shape-generic Metal moe_gemv with the chosen sub-4-bit dequant in-shader, (2) top-16/E=896 select, (3) KDA decode step (state is 128×128/head — start on CPU NEON, it's cheap per token), (4) parameterized MLA fused decode for the ~23 full-attention layers, (5) AttnRes (trivial FLOPs, correctness-first), deferring prefill MMA GEMMs to week two.

### 9. K3's resident (non-expert) RAM footprint was never computed, and the memory plan has unresolved interactions
The 30–40GB expert-cache assumption presumes a small resident set, but nobody summed K3's embeddings (163840×hidden ×2), ~93 layers of attention/KDA/conv/AttnRes/router/norm weights, and shared experts at the chosen precision — if that is 20–25GB (plausible at 93 layers), the cache drops to ~25GB and gap 5 worsens. Unresolved: mlock (vm.user_wire_limit 52.5GiB) vs Metal wiring (iogpu.wired_limit_mb=0 default, sysctl behavior on macOS 26 unverified) double-accounting; the box **already showed 28.5GB swap in use** during benchmarks (dirty measurement environment, and the compressor will fight streaming); no DISPATCH_SOURCE memory-pressure response.
**Close it:** a one-page RAM ledger auto-generated from config.json on drop day; add `vm_stat`/`memory_pressure` capture to the bench harness; reboot/clear swap before every benchmark; empirically find the --ram knee (M4 Pro 48GB→38 suggests ~50–52 on 64GB).

### 10. Licensing and access mechanics
Verified: colibri Apache-2.0, ds4 MIT — forking/mixing is clean (attribution + NOTICE for Apache). Unverified: K3's own license (K2.5 was Modified-MIT — fine for this use, but K3's text is unseen), whether the HF repo requires gate acceptance (the persistent 401 suggests token-authenticated access at minimum — a human click-through blocks automation), whether ModelScope mirrors K3 day-1 (colibri's downloader prefers ModelScope for throughput), and `modeling_*.py` is trust_remote_code that should be read before executing in the oracle harness.
**Close it:** at drop, read LICENSE + gate terms first; pre-provision `HF_TOKEN` and test `huggingface_hub`+`hf_transfer` auth against a gated repo today; check `modelscope.cn/api/v1/models/moonshotai/Kimi-K3` in parallel.

## Secondary gaps (fold into the plan, below top-10)
- **Vision tower**: "skip for text-only" asserted, never designed — tensor identification, config surgery, and whether the text stack references vision embeddings are unknown; multimodal support should be explicitly declared out of scope for v1.
- **Speculative decoding trade-off unanalyzed**: Kimi-Linear-48B draft costs ~25GB resident (vs expert cache!) and acceptance rate on K3 outputs is unmeasured; MTP presence unknown (all K2s shipped `num_nextn_predict_layers=0`; colibri issue #8 shows the head must be int8 if it exists).
- **External TB4 SSD is assumed in several improvement ideas but its existence/speed on this machine was never inventoried.**
- **SSD sustained/thermal behavior**: 6.6GB/s was measured in bursts; hours-long 100%-duty streaming throughput and any thermal derating unmeasured; also MacBook-on-battery power throttling unstated (assume mains).
- **ds4 download_model.sh / colibri download_fp8.py both need adaptation** (hardcoded repos; colibri's `DEST` is a Windows drive path).
- **Debuggability**: colibri's PIPE-mode non-determinism (~7-token divergence) means the correctness harness needs the serial validation configs preserved in the K3 fork.
- **Benchmark harness**: adopt ds4-bench's frontier/steady-state split + CSV from day one or the plan's tok/s claims will be incomparable across iterations.

- Make the drop-day deliverable a router-trace study, not kernels: per-layer oracle over ~1M calibration tokens dumping expert selection frequencies and cross-layer co-activation (extend colibri expert_atlas/route_pairs.py and ds4's hotlist profiler) to produce the hit-rate-vs-pin-GB curve that decides between 0.3 and 2 tok/s and whether expert pruning is mandatory
- Adapt colibri's convert_fp8_to_int4.py rather than writing a new converter: add an MXFP4 e8m0-per-32 branch next to the existing NVFP4 e2m1 LUT (lines 138-144), a K3 tensor classifier (KDA/conv/AttnRes/vision skip-list), and [E,...] expert un-stacking into file-adjacent 4KiB-aligned gate/up/down triplets with 16KiB slab alignment for Metal no-copy
- Build the per-layer PyTorch oracle harness first (streams ~18-23GB of one layer's weights at a time, fits in 64GB) and extract activation fixtures for KDA/SiTU/AttnRes/MLA/router before writing any C/Metal kernel — silent-garbage risk from three brand-new ops is the plan's biggest correctness hole
- Sequence the Metal port by dependency, not ambition: (1) shape-generic moe_gemv with in-shader sub-4-bit dequant, (2) top-16-of-896 two-level select (r_top8_par caps at E<=256), (3) KDA decode step on CPU NEON first (state is only 128x128/head), (4) parameterized MLA fused decode for the ~23 full-attention layers, (5) AttnRes; defer prefill MMA GEMMs to week two

- Tier the storage instead of uniform 3-bit: keep hottest experts (by router-trace rank) at native MXFP4 (QAT-exact fidelity) and cold tail at 2-2.5bpw, sized so total = ~1.05TB; benchmark cfse nibble-rANS decode MB/s per E-core before adding the lossless layer, since its ratio on non-white MXFP4/IQ3 payloads is unmeasured
