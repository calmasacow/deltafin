# DwarfStar (ds4) GPU + distributed deep-read — research/ds4

Scope: metal/*.metal (19 files, ~21.7k lines), ds4_metal.m (39,615 lines, host runtime), ds4_gpu.h/_args/_mgpu, ds4_tp.c/h, ds4_distributed.c/h, ds4_bench.c, README/MODEL_CARD/AGENT/STRIXHALO. Target models: DeepSeek-V4-Flash (284B total / 13B active, 43 layers, 384 routed experts, compressed sparse attention, HC=4 hyper-connections) and GLM 5.2 (MLA-style low-rank attention, 6144 embd).

## 1. Metal kernel inventory and quality

The Metal library is **compiled from source at process start** (all .metal files concatenated by `ds4_gpu_full_source()`, `ds4_metal.m:5741`), with per-device macros. Pipelines are cached by name+function-constants.

**flash_attn.metal (1441 lines)** — llama.cpp/ggml `kernel_flash_attn_ext` lineage, heavily specialized:
- 5 kernels: `_pad` (pads trailing partial K/V/mask block to full 32/64-row chunks, :139), `_blk` (mask scan marking 8×64 blocks as skip/all-zero/needed, :208), main non-vec prefill (:279-914), `_vec` decode (:951-1370), `_vec_reduce` (split-K combine, :1401).
- Non-vec: Q=8 query rows/threadgroup, C=64 KV cols per block, NSG=4 or 8 simdgroups (function constant :274). Q/K/V staged as **half** in threadgroup memory; QK via `simdgroup_load` (transposed K) + `simdgroup_multiply_accumulate` into `simdgroup_float8x8` (fp32 accumulation, :520-561); PV likewise fp32-accumulated (:669-744). Online softmax entirely fp32 (running M/S per row, `simd_max`/`simd_sum`, :625-664). Supports ALiBi (`has_bias`), logit softcap (tanh), attention sinks, broadcast mask — all via function constants so dead code is stripped.
- Decode vec kernel: 1 query row, C=32, NE=4 lanes cooperate per KV row, `dot(float4,float4)` fp32 accumulation, `simd_shuffle_down` tree reductions, **split-K across NWG workgroups** with fp32 (S,M) partials and a separate reduce kernel — exactly the right shape for long-context single-token decode.
- Exported instances only: DK=DV=512 f16 (DS4's 512-wide raw KV rows; MLA-class dims) and DK=DV=256 (GLM) for prefill; DK=DV=512 for decode vec (:928-933, :1391).
- Quality: state of the art for Metal. Correct simdgroup-matrix use, threadgroup staging, 2×-unrolled dual loads, function-constant specialization, block skipping, split-K. **fp16 storage, fp32 accumulation everywhere; no bf16 anywhere in the tree.**

**dense.metal (2389 lines)** — matvec family `kernel_mul_mv_*` (q8_0 with r4/pair variants; `mul_mv_ext` register-blocked r1_2..r1_5 for f16/q8_0/q4_0/q4_K); fused shared-expert kernels `kernel_dsv4_shared_gate_up_swiglu_q8_0(_r4)` (:481-539); tiled GEMM `kernel_mul_mm` (64×32 tile, NK=32, inline dequant to half, `simdgroup_half8x8` operands, `simdgroup_float8x8` accumulators, :1736+). Additionally `kernel_mul_mm_mpp`/`_mpp_direct_rhs` and `*_nax_*` variants use **Metal 4 tensor_ops (MetalPerformancePrimitives cooperative tensors / matmul2d)** — gated by `DS4_METAL_HAS_TENSOR`, which is enabled **only on M5/A19-class devices** (`ds4_metal.m:2360-2394`: requires `MTLGPUFamilyMetal4` AND device name "M5"; explicitly "disabled for pre-M5/pre-A19 devices"). **On M1 Max you get the classic simdgroup path — nothing to lose there.**

**moe.metal (7858 lines)** — ~70 exported kernels; see §2.

**Elementwise/support**: norm.metal (fused `rms_norm_mul`, `add_rms_norm_mul`, `qkv_rms_norm`), softmax (with sinks), argsort (bitonic + merge), glu, unary (incl. `softplus_sqrt`), bin (`add2`/`add3` fusion), cpy (incl. `kernel_dsv4_flash_kv_stage_f16`), get/set_rows (quantized get_rows for q8_0/q4_0/q4_K), sum_rows, repeat, concat.

Precision policy across the tree: quantized weights dequantized inline (to half for GEMM tiles, to fp32 scalars in matvecs), activations fp32, accumulation fp32, KV f16 (with fp8-emulation round-trip, §6), optional f16 "mid" MoE activations to halve bandwidth (`kernel_dsv4_moe_swiglu_weight_f16`, moe.metal:229 — comment: grouped matmul converts to half before MMA anyway, so this cuts the mid write/read traffic for free).

## 2. MoE kernels: batching, dispatch, streaming

**Decode (n_tokens=1..few)** — fused matvec kernels, one dispatch per projection stage per layer:
- `*_pair_swiglu_*`: gate and up matvecs fused + `silu(g)*u*route_weight` computed in-kernel (e.g. `kernel_glm_q4_K_pair_swiglu_f32` moe.metal:414: grid = (mid_rows, slot, token), 256-thread threadgroup reduction; simdgroup variants with N_R0 row-blocking for q2_K/q5_K, :477-616). Route weight read from GPU-resident router output — **no CPU involvement in routing**.
- `*_sum6_f32`/`*_sum8_f32`: down-projection matvec fused with the 6- or 8-slot weighted accumulation (`kernel_mul_mv_id_q4_K_sum6_f32` etc., :5477-6980), so the entire routed FFN for a token is ~2 dispatches per layer.
- Quant coverage: q2_K, q4_K, q5_K, q6_K, q8_K, q8_0, iq2_xxs (with the iq2 grid/sign LUTs in constant memory :17-97).
- TP-aware: `ds4_tp_owns_expert()` inline (:160) — unowned experts write zeros; args carry tp_rank/world/expert_base (:137-157).

**Prefill (batched)** — ggml-style two-phase: `kernel_mul_mm_id_map0<ne20>` builds an **expert-major token map** in one threadgroup (per-expert row counts `htpe` + flattened ids `hids`, :6984-7049, instantiated for top-k = 1..22), then `kernel_mul_mm_id` (:7055) runs a 64×32-tile GEMM per (expert, tile): NK=32 panels staged in threadgroup memory, inline dequant, `simdgroup_float8x8` accumulation, results scattered back token-major (:7249-7270).

**Streamed experts → GPU zero-copy**: three mechanisms, all built on unified memory:
1. **Address tables**: `*_addr_*` kernels take `device const uint64_t *gate_addrs/up_addrs/down_addrs` — per-expert raw GPU VAs — and `reinterpret_cast<device const char*>(addr)` (:643-700, mm variant :7277-7317). Addresses are `[buffer gpuAddress] + inner` (ds4_metal.m:11748-11756, macOS 13+). A null address ⇒ kernel writes zeros (deterministic miss behavior).
2. **Masked dispatch**: `*_masked` variants take `active_mask` (bit per slot, :702-718) so the host can compute **resident experts first while missing ones stream from SSD**, then dispatch the complement — this is the latency-hiding path demanded by AGENT.md:11.
3. **GPU-side validation**: `kernel_stream_expert_cache_validate` (:4297-4332) checks the addr tables against the GPU-resident selected ids and writes miss/invalid bitmasks to a status buffer (max 384 experts hardcoded).

**Host cache** (ds4_metal.m:541-600): static table `g_stream_expert_cache[80][384]` of entries {gate/up/down MTLBuffer, abs offsets, last_used, use_count, inflight_seq, slab_slot}; 256 slab pools; hotness-decay LRU; shipped hot-expert profiles (`ds4_streaming_hotlist*.inc`, 192KB+94KB of layer/expert priors) seed the cache. In-flight sequence numbers (ds4_metal.m:1019-1097) prevent buffer reuse while a committed CB still references an entry.

**SSD→buffer path**: explicit `pread` from the GGUF fd **directly into `[buffer contents]`** of MTLStorageModeShared buffers (ds4_metal.m:10824-10868) — no memcpy, no mmap page-cache faulting. Parallel pread pool: default **9 threads, max 18** (`DS4_METAL_STREAMING_EXPERT_PREAD_THREADS`, :10802-10815), persistent workers with generation counters (:10884-11001). Per-layer/pread telemetry throughout (:3340-3440).

**Decode streaming overlap**: routing runs on GPU; host encodes `encodeSignalEvent` on a MTLSharedEvent after router output (`ds4_gpu_signal_selected_readback_ready`, ds4_metal.m:8197-8221), commits the CB, `waitUntilSignaledValue` (60s timeout), reads 6-8 selected ids from shared memory, preads misses, updates addr tables, continues encoding — GPU keeps executing the already-committed shared-expert/attention work during the CPU I/O.

## 3. Host-side Metal runtime

- **Buffer strategy**: model weights are mmapped once and wrapped with `newBufferWithBytesNoCopy` into a **small number of page-aligned overlapping views** (ds4_metal.m:1680-1821): adjacent views overlap by `max_tensor_bytes + page` so every tensor lies wholly in ≥1 view (hot path = 1 buffer + inner offset, "never split a weight tensor across command encoders"); view size capped at `maxBufferLength` (128GiB default cap for distributed span maps to keep VM validation off the first-command path, :1758-1768); up to 4096 views. Storage: `MTLResourceStorageModeShared` (+ optional `MTLResourceHazardTrackingModeUntracked` via env, :1145-1151). **MTLResidencySet** wires the views (:1831-1836, macOS 15 API at :1648, :15188), then a coarse-stride warm pass validates page tables before timed execution (:1839-1864). Scratch buffers are Shared (Private only on M5 and only when not CPU-visible, :1129-1189). Transient per-dispatch buffers Shared, released when the owning CB completes.
- **Command batching**: single `MTLCommandQueue`; one long-lived "batch" command buffer with **one open compute encoder reused across all dispatches** (`g_batch_cb`/`g_batch_enc`, :52-53, :879-908); encoder is closed only for blits/event ops. `flush_commands` commits into a pending list without waiting (:8159-8180); `end_commands` commits + waits all pending + owned.
- **CPU-GPU sync per token** (resident Metal decode, ds4.c:29256-29275 → `metal_graph_eval_token_raw_swa`): **one `begin_commands`, the entire 43-layer graph + output head encoded, one `end_commands` (single waitUntilCompleted), one logits readback** (`ds4_gpu_tensor_read` of n_vocab f32, ds4.c:29228), then CPU argmax/sampling. ≈1 sync/token + one small readback. SSD-streaming decode without the static map does per-layer begin/end (43 CB waits/token, ds4.c:29179-29218); the "batch_static_decode" path (ds4.c:29126-29173) restores one-CB-per-token by pre-mapping a static decode address map.
- TP gates do **not** break the command buffer: GPU arrival is a 1-thread flag-store kernel + buffer hazard, release is `encodeWaitForEvent` on a CPU-signaled shared event (§5), so a token with 86 gates is still one CB.

## 4. GPU args / multi-GPU

- `ds4_gpu_args.c`: `--gpu-vram N[,N…]`/`--gpu-devices` parser → `ds4_gpu_config` (≤16 devices, per-device byte budgets, 512MB default safety margin); `auto` requires CUDA (`#if !defined(__APPLE__)`, :152) — **on Apple this whole layer is inert**.
- `ds4_gpu_mgpu.h`: **CUDA-only** multi-GPU plumbing: `g_gpu[16]` per-device contexts (stream/cublas/scratch/budget/boundary event), peer-capability matrix, device-tagged tensors, xdev copies (peer-async or pinned-host bounce, grouped `xdev3` handoffs for pipelined prefill slots), managed-memory KV alloc, strict per-device weight-cache lookup. `--cuda-tensor-parallel` arranges N devices as N/2 layer-pipeline "homes" + N/2 TP "partners" with 50/50 expert split and row-sharded vocab head (README:700-724; tested 8×L40S: 120 t/s aggregate gen, 2000 t/s prefill). **Metal is strictly single-GPU**; multi-Mac scaling is ds4_tp/ds4_distributed instead.

## 5. Tensor parallel over Thunderbolt RDMA + pipeline parallel over TCP

**ds4_tp.c — 2-rank lockstep TP (Metal only)**:
- Wire: host little-endian (both ranks identical Apple Silicon by definition); hello magic `0x44533454` doubles as byte-order check, protocol v7 (:40-42); identity (model id, layers, embd, vocab, quant bits, ctx, gate schedule) must match or abort. Control = blocking framed TCP; data = RDMA or dedicated full-duplex TCP.
- **AppleThunderboltRDMA quirks** (validated in-code, :118-131): only UC queue pairs (RC/UD ENOTSUP); RDMA WRITE accepted but never executes ⇒ **two-sided SEND/RECV only**; **max 16KB per message**; RTR needs GRH with the IPv4-mapped GID of the TB member interface. UC is in-order and the gate sequence is deterministic (**DS4: 86 gates/token = 43 layers × {ATTN,FFN}**; GLM: one FFN gate per sparse layer), so decode pre-posts a 16-deep recv window keyed by seq — recv completion IS the arrival signal. Bulk prefill path: 64 × 16KB slots.
- Per-gate payload: fp32 partial vector `n_embd*4` bytes ("never quantized on the wire", ds4_tp.h:118) — DS4 16KB = one RDMA message; GLM 24KB = 2 ordered messages (README:660-661). TCP fallback = symmetric writev(header+payload)/read with desync-detecting 16-byte header (ds4_tp.c:1428-1468). Big prefill gates: registered-slab bulk RDMA or interleaved 2MB TCP rounds (:1543-1582).
- **GPU↔CPU gate handshake** (ds4_metal.m:8367-8709): GPU publishes arrival by storing the seq into a shared slab word via a 1-thread kernel (`kernel_dsv4_tp_flag_set`), ordered after the partial-output kernels by the buffer hazard; the QOS_USER_INTERACTIVE service thread **spin-reads the flag word (~1-3µs detection vs 10-20µs for MTLSharedEvent.signaledValue polling; worth +2.3 t/s measured)**, runs the exchange, then releases the GPU by setting `signaledValue` on the CPU event that the CB is `encodeWaitForEvent`-blocked on. Failure still releases (latched failure flag) so the GPU never deadlocks.
- **DVFS keep-alive** (:8401-8469): dedicated queue + thread continuously dispatching a 1.2M-iteration ALU-only kernel, because gate stalls let the frequency governor sag (~1.7× solo-vs-engine kernel-time gap observed); paused during verify blocks (pure parasite there, ~2.3ms/5-row block).
- Splits: routed experts 50/50 contiguous per rank (dense/attention/shared/embed/output replicated); GLM prefill additionally splits attention heads 50/50 (:8344-8366) with one bulk partial-sum exchange per layer per stage; vocab-split output head (worker ships logits half over control socket); speculative verify blocks exchange ≤8 rows in one batch gate.
- Measured (2× M5 Max 128GB, TB5, GLM 5.2 IQ2_XXS 188GiB, README:663-668): **decode ~16.8 t/s vs 4.8 t/s single-Mac SSD streaming (3.5×); prefill 4096 ~94 t/s vs 3-5 t/s (~20×)**. Startup ~9s/machine (pre-fault ~100GiB shard + residency set).

**ds4_distributed.c — pipeline parallel over plain TCP** (any platform): coordinator + workers own contiguous layer slices (`--layers 10:20`, `N:output`); worker-to-worker activation forwarding (route carried in WORK frames; A→B→C→A); fp32 activations (`DS4_DIST_ACTIVATION_BITS_DEFAULT 32`, :65); prefill pipelined in 4096-token chunks → **1.38×/1.66×/1.85× prefill speedup at 9k/29k/64k tokens on 2 Macs**; decode strictly serial → **19.4% slower** than single-process (30.59→24.67 t/s, TB5) (README:409-420). Link sensitivity: TB5 0.45ms ping → 583/25.1 t/s; WiFi 77ms → 251/10.7; VPN 152ms → 115/3.6 (README:502-504). Two 512GB M3 Ultras run PRO Q4 (1.6T) at 11.47 t/s with balanced per-layer telemetry (README:449-455).

**Two Macs for K3 on M1 Max?** TP mode requires each rank to hold half the routed experts resident — 2.8T even at ~2bpw ≈ 700GB ≫ 2×64GB, so TP is out. TCP pipeline mode needs the full model split across machines (128GB combined, still far short) and makes decode slower anyway. The transferable assets are the *mechanisms*: flag-word gate arrival, in-CB event waits, keep-alive kernel, deterministic gate schedule with pre-posted recv windows.

## 6. dsv4-specific kernels → what a K3 port needs

- **dsv4_rope.metal**: partial "RoPE tail" — copies the n_nope prefix, rotates only the n_dims tail; full YaRN (jquesnelle/yarn port, :49-80); neox + adjacent-pair modes; in-place pair specialization with lane-mapping kept bit-identical to reference (:191-253); shared4 variant (4 heads reuse threadgroup-computed cos/sin, :260); affine-position variant computes positions in-kernel, eliminating the pos buffer (:334). DS4 uses n_dims=64. **Directly reusable for K3's MLA rope-tail (64-dim rotary on 576-dim q/k).**
- **dsv4_kv.metal**: FP8 **E4M3FN emulation** of the KV cache — per-64-element amax → power-of-2 scale → nearest-even E4M3 found by 7-step binary search *in shader* (:58-91), value written back dequantized so cache buffers stay float-addressable (:111); decode-side fused store writes both the fp8-rounded value and the **f16-rounded raw row that FlashAttention consumes** (:215-272). Indexer path: 128-wide in-place **Hadamard** butterfly in threadgroup memory + per-32-block amax → **FP4 E2M1** quant-dequant simulation (:163-209). Ratio-4 compressor pack/shift/store_one kernels manage the recurrent 8-row time-axis KV compression state (:278-369).
- **dsv4_hc.metal**: Manifold-Constrained Hyper-Connections (HC=4 residual streams): mixer row split into sigmoid pre-weights, 2·sigmoid post-gates, and a 4×4 combination matrix normalized by **Sinkhorn iterations** (:127-296); fused decode kernels do split+weighted-sum(+RMS norm) in one dispatch, and expand(+q8_0 quantize of the output) (:302-987). Numerics warning in-code: tanh-form vs exp-form sigmoid diverge on M5's fused path (:100-122).
- **dsv4_misc.metal (6157 lines)**: GPU routers (`kernel_dsv4_router_weights_one/finalize_one(_simd)`, `topk_mask(_scatter)`, row sort), indexer scoring (tiled f32/f16/nax), `kernel_dsv4_indexed_mixed_attention_heads8` (decode over raw window + selected compressed rows), softmax_pool ratio-4, compressor APE scores, `kernel_dsv4_tp_keepalive`/`tp_flag_set`; plus the **GLM MLA-family kernels: kv_lora_rms_norm, k_b_project_q8_0, store_compact_kv, qk_lowrank_q8_0 (+batch/sg/t4), value_project_q8_0 (+batch heads +mma), indexed decode split_group8 partial+reduce (split-K sparse attention over top-k rows), indexed batch attention (several group widths, causal), build_kv_cache (+flash staging)** (:545-4577).
- **K3 port needs**: (a) MLA compressed-KV store + absorbed decode attention — GLM's compact-KV/qk_lowrank/value_project kernels are the closest existing template, and the 512-wide FA instantiation already matches MLA's 512-dim latent; (b) rope-tail as-is; (c) router/topk kernels with K3's expert count/top-k/scoring (sigmoid+bias grouping is a small edit); (d) regenerate the fused pair_swiglu + sumK matvec family for K3's expert dims/quant; (e) **no** HC, indexer, Hadamard, or compressor machinery unless K3 has analogous features — that's roughly half of the dsv4-specific surface you can skip.

## 8. What is NOT GPU-accelerated, and why

- **Sampling/logits**: logits are read back to CPU every token (one `ds4_gpu_tensor_read` of n_vocab×4B, ds4.c:29228); argmax/top-p/temperature all CPU (`sample_argmax` ds4.c:36581). Cheap on unified memory; keeps sampling code simple/portable.
- **Tokenizer, chat templates, GGUF metadata parsing, session/KV snapshot serialization** — CPU (ds4.c); metadata is deliberately never bound to Metal (view wrapper covers tensor data only, ds4_metal.m:1709-1712).
- **SSD expert streaming I/O**: explicit multi-threaded `pread` on CPU (9-18 threads) into shared buffers — deliberately *not* mmap faulting, to keep memory pressure and page-cache behavior controlled (AGENT.md:11).
- **TP/distributed transport**: CPU service threads (verbs post/poll or TCP), spin-wait arrival, exchange, event release. RDMA is host-initiated by platform necessity (no GPU-initiated networking on Metal).
- **CPU inference backend exists but is reference/debug only** (AGENT.md:12); everything numerically hot — embedding, norms, rope, attention (incl. indexer/top-k selection), routing, MoE, output head — is on GPU in the Metal path. Router/top-k being GPU-resident is what makes the one-CB-per-token decode possible; the only mid-token CPU involvement is the streaming-mode selected-ids readback via shared event.

## KEY FACTS
- ds4 Metal path is single-GPU; multi-GPU (ds4_gpu_mgpu.h) is CUDA-only. Metal scaling across Macs = ds4_tp.c (2-rank TP over Thunderbolt RDMA/TCP) or ds4_distributed.c (layer-pipeline over TCP).
- Flash attention (metal/flash_attn.metal) is llama.cpp-lineage: fp16 K/V storage, simdgroup_half8x8 operands, simdgroup_float8x8 fp32 accumulation, fp32 online softmax; prefill Q=8/C=64 with mask-block skipping; decode is a split-K vec kernel (C=32, NE=4, NWG workgroups + reduce). Only DK=DV=512 (DS4/MLA-class) and 256 (GLM) instances are exported. No bf16 anywhere.
- Metal-4 tensor_ops (MetalPerformancePrimitives matmul2d, the 'mpp'/'nax' kernels) are gated to M5/A19 devices only (ds4_metal.m:2360-2394); on M1 Max the simdgroup path is the only and correct one.
- MoE decode = fused kernels: gate+up matvec + swiglu + route-weight in one dispatch (pair_swiglu), down-proj + 6/8-slot weighted sum in another (sum6/sum8); prefill = expert-major map0 + 64x32-tile mul_mm_id GEMM. Routing (router weights, top-k) runs entirely on GPU.
- Streamed experts reach the GPU zero-copy: CPU pread pool (default 9, max 18 threads) reads from the GGUF fd directly into MTLStorageModeShared buffer contents; kernels consume per-expert uint64 gpuAddress tables ('addr' kernels reinterpret_cast raw device addresses); 'masked' kernel variants let resident experts compute while misses stream; a GPU kernel (kernel_stream_expert_cache_validate) checks addr tables against selected ids.
- Streaming expert cache: static 80-layer x 384-expert entry table, slab pools, LRU+hotness with shipped hot-expert profiles (ds4_streaming_hotlist*.inc), in-flight seq numbers to protect buffers referenced by committed command buffers.
- Model weights: mmap + newBufferWithBytesNoCopy into a few page-aligned OVERLAPPING shared-storage views (overlap > max_tensor + page so every tensor is wholly inside one view); MTLResidencySet wires them; coarse warmup pass validates page tables before timing.
- Resident Metal decode = ~1 CPU-GPU sync per token: one command buffer encodes all 43 layers + output head, one waitUntilCompleted, one n_vocab*4B logits readback, CPU sampling. One MTLCommandQueue, one long-lived compute encoder reused across dispatches.
- TP wire: AppleThunderboltRDMA supports only UC QPs, two-sided SEND/RECV (RDMA WRITE silently no-ops), 16KB max message; DS4 exchanges 86 gates/token (43 layers x ATTN+FFN), each an fp32 partial of n_embd*4 bytes (16KB DS4, 24KB GLM split in 2 messages); GPU publishes gate arrival via a 1-thread flag-store kernel into a shared slab word (CPU spin-read detects in 1-3us vs 10-20us for MTLSharedEvent polling, +2.3 t/s), release via encodeWaitForEvent - gates never break the command buffer.
- TP needs a DVFS keep-alive: a dedicated thread continuously dispatches a 1.2M-iteration ALU kernel because gate stalls make the GPU governor down-clock (~1.7x kernel-time inflation observed).
- TP measured (2x M5 Max 128GB, TB5, GLM 5.2 IQ2_XXS 188GiB): decode 16.8 t/s vs 4.8 t/s single-Mac SSD streaming; prefill 4k 94 t/s vs 3-5 t/s. Pipeline-TCP mode: prefill 1.38-1.85x faster with 2 Macs, decode 19.4% SLOWER; ping latency directly caps decode (77ms WiFi -> 10.7 t/s).
- Speed table (DSv4 Flash, 13B active, q2): M3 Max 26.7 t/s decode / 250 t/s long prefill; M2 Ultra 23.2 t/s; M4 Max 26.8 t/s; M5 Max 34.3 t/s / 463 t/s; M3 Ultra 36.9 t/s. M1 Max (~400GB/s) extrapolates to roughly 11-13 t/s decode for a resident 13B-active q2 model.
- DSv4-specific GPU ops: partial RoPE tail with YaRN (reusable for K3 MLA), FP8 E4M3FN KV emulation via in-shader binary search + f16-rounded raw rows for FA, FP4+128-wide-Hadamard indexer simulation, ratio-4 KV compressor, HC=4 hyper-connections with Sinkhorn-normalized 4x4 mixing, GPU router/topk, GLM MLA kernels (kv_lora_rms_norm, qk_lowrank, value_project, compact-KV store, indexed split-K sparse attention).
- Not GPU-accelerated: tokenizer, sampling (per-token CPU argmax after logits readback), GGUF parsing, snapshot serialization, SSD I/O (explicit CPU pread by design, not mmap faults), RDMA/TCP transport threads. CPU inference backend is reference/debug only.
- ds4-bench methodology: frontier walk measuring only newest suffix prefill, greedy non-EOS decode with first-token vs steady-state split, snapshot/restore excluded from timing; CSV output.
- TP across two 64GB Macs cannot host Kimi K3 (2.8T at ~2bpw is ~700GB vs 128GB combined); expert split requires both halves resident. Single-machine SSD streaming is the only ds4-style option on M1 Max 64GB.

## IMPROVEMENT IDEAS
- Adopt ds4's streaming-expert architecture wholesale for K3 on M1 Max: MTLStorageModeShared per-expert buffers filled by a multi-threaded pread pool (9+ threads saturate Apple NVMe random reads), uint64 gpuAddress tables consumed by addr-variant kernels, masked dispatch so resident experts compute while misses stream, and GPU-resident routing with a single shared-event selected-ids readback per layer.
- Beat ds4's streaming decode by replacing its per-layer command-buffer break (streaming mode) with the TP-gate pattern it already proves elsewhere: encode the whole token in one CB with encodeWaitForEvent after each layer's router, have the I/O thread signal the event once the missing experts' preads land - GPU never drains, CPU I/O fully overlaps.
- K3's expert working set per token is small (top-8-ish of ~hundreds of experts x ~60 layers); size the expert cache with ds4's auto-plan formula (80% of recommended working set minus non-routed weights) and seed it with an offline hot-expert profile (ds4 ships per-layer hotlists; generate one for K3 from a calibration run) - on 64GB expect ~40-48GB of expert cache.
- Reuse ds4's fused-kernel shapes rather than generic GEMMs: pair_swiglu (gate+up+activation+route-weight in one dispatch) and sumK (down-proj + weighted accumulation) cut dispatches to ~2 per MoE layer per token; write the K3 variants for its expert dims and chosen quant (q2_K/iq2_xxs for capacity, q4_K if bandwidth allows).
- Port the DK=512 flash-attention instantiation for K3's MLA absorbed decode (512-dim latent matches DS4's raw KV rows exactly); take GLM's kv_lora_rms_norm / qk_lowrank / value_project / compact-KV-store kernels as the MLA template; keep KV f16 with fp32 softmax; skip DSv4's HC/indexer/Hadamard/compressor machinery entirely.
- Add the DVFS keep-alive kernel during SSD-miss stalls: M-series GPUs down-clock in idle gaps (~1.7x kernel-time inflation measured by ds4); a 1-threadgroup ALU spin kernel on a second queue keeps clocks up while decode waits on NVMe - likely a free 10-30% on streaming decode.
- Write mid MoE activations as f16 (ds4's kernel_dsv4_moe_swiglu_weight_f16 trick) and keep all accumulation fp32; on a 400GB/s M1 Max every halved intermediate matters more than on Ultra-class parts.
- Use one command buffer per decode token with a single logits readback and CPU sampling (ds4's resident-path shape); avoid any mid-token synchronize except the one selected-ids event in streaming mode.
- Wrap the K3 GGUF with a handful of overlapping newBufferWithBytesNoCopy views + MTLResidencySet for the resident (non-expert) weights, with a coarse-stride warmup before benchmarking - ds4 shows first-touch VM validation otherwise pollutes the first tokens.
- Copy ds4-bench's harness design (frontier suffix-prefill timing, first-token vs steady decode split, snapshot restore between frontiers, CSV) for apples-to-apples comparisons against colibri.
- Do not plan on two-Mac scaling for K3 on 64GB machines: ds4's TP needs both expert halves resident (impossible at 2.8T) and its TCP pipeline slows decode; if a second machine appears, use it only for pipelined prefill of huge prompts.
- Steal the explicit-pread-not-mmap rule for expert streaming: ds4 deliberately reads expert blobs with pread into pre-allocated shared buffers to keep page-cache pressure bounded on unified memory - critical on 64GB where mmap faulting of a 700GB+ file would thrash.
